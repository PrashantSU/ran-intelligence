# Telecom RAG System

## 1. Purpose

The Telecom RAG system will allow engineers to search and ask questions about technical documentation related to 4G and 5G networks.

The system will retrieve relevant information from technical specifications, research papers, reports and other selected documents. A language model will then use the retrieved content to produce an answer with references to its sources.

The goal is to make technical information easier to find without relying entirely on the language model's internal knowledge.

This component will be designed specifically around telecom engineering topics, including:

- 5G NR architecture.
- Radio resource management.
- Beamforming and MIMO.
- Scheduling and resource allocation.
- Mobility and handover.
- Radio measurements.
- Interference management.
- Network performance and troubleshooting.
- O-RAN architecture.

The system should distinguish between information found in a source document and explanations generated by the model.

## 2. Document Sources

The initial knowledge base will use publicly accessible technical documents.

Potential sources include:

| Source | Content |
|---|---|
| 3GPP | LTE and 5G NR specifications |
| ETSI | Telecommunications standards and technical reports |
| O-RAN Alliance | Open RAN architecture and interface specifications |
| Research papers | Academic work on wireless networks and network intelligence |
| Technical reports | Public telecom engineering reports and documentation |

We will start with a small collection of relevant documents rather than indexing thousands of files immediately.

Each document should have its source URL, title, version and other available metadata recorded.

Redistribution rights will be checked before committing documents to GitHub. Documents that cannot be redistributed will be downloaded separately for local indexing.

## 3. RAG Architecture

The system will have two main workflows.

### 3.1 Document Indexing

Documents are processed before they can be retrieved.

```text
Technical Documents
        |
        v
Document Loading
        |
        v
Text Extraction
        |
        v
Cleaning and Normalisation
        |
        v
Document Chunking
        |
        v
Metadata Attachment
        |
        v
Embedding Generation
        |
        v
Vector and Keyword Indexes
```

The output is a searchable knowledge base.

### 3.2 Question Answering

When an engineer submits a question, the system retrieves relevant information and uses it to generate an answer.

```text
User Question
      |
      v
Query Processing
      |
      v
Hybrid Retrieval
      |
      v
Candidate Ranking
      |
      v
Context Selection
      |
      v
LLM Generation
      |
      v
Answer with Citations
```

The retrieval and generation stages will be evaluated separately so that we can identify whether a problem comes from retrieval or the language model.

## 4. Document Ingestion

The document ingestion pipeline will support common technical document formats.

Initial formats:

- PDF.
- TXT.
- Markdown.
- HTML, where needed.

PDF documents will be the main source initially.

The ingestion process should:

1. Load the document.
2. Extract its text.
3. Preserve page information where possible.
4. Identify document metadata.
5. Clean extraction artefacts.
6. Split the content into chunks.
7. Store the resulting chunks and metadata.

PDF extraction can be imperfect, particularly with tables, mathematical expressions and multi-column layouts. We should inspect extracted text for important documents instead of assuming that extraction is always correct.

## 5. Document Chunking

Documents will be split into smaller sections before embedding.

The purpose of chunking is to make retrieval more precise while preserving enough context for the language model to understand the retrieved information.

The initial implementation will use recursive character-based chunking.

Possible starting configuration:

- Chunk size: approximately 800 tokens.
- Chunk overlap: approximately 120 tokens.

These values are initial experiments, not fixed requirements.

We will compare different chunk sizes and overlap settings during retrieval evaluation.

Where possible, chunks should respect document structure, such as:

- Section headings.
- Subsections.
- Paragraph boundaries.
- Specification clauses.

A chunk should retain enough information to identify its original document and location.

## 6. Metadata Management

Every chunk should retain metadata about its original source.

Initial metadata fields:

| Field | Description |
|---|---|
| chunk_id | Unique chunk identifier |
| document_id | Original document identifier |
| document_title | Document title |
| source | Publisher or organisation |
| source_url | Original document location |
| document_version | Version, if available |
| section | Section or subsection |
| page_number | Page number, if available |
| chunk_index | Position within the document |
| content | Extracted text |
| licence | Licence or access information |

Metadata will be used for filtering, citation generation and document traceability.

The system should not generate a citation when it cannot identify the supporting source.

## 7. Embedding Generation

Embeddings represent text as numerical vectors that capture semantic information.

The system will convert document chunks into embeddings and store them in a vector index.

The initial implementation will use Sentence Transformers.

Candidate models include:

- `sentence-transformers/all-MiniLM-L6-v2`
- `BAAI/bge-small-en-v1.5`

Both are available as downloadable models and can be used locally.

We will begin with one model and compare alternatives only if retrieval quality requires it.

The embedding model used for indexing and querying must be compatible. If the model changes, the document embeddings should be regenerated.

## 8. Vector Search

FAISS will be used for initial vector search.

It provides an efficient way to search through document embeddings using similarity measures.

The first implementation can use a simple exact similarity index. More advanced indexing configurations can be introduced if the document collection becomes large.

The retrieval system should return:

- Retrieved chunk text.
- Similarity score.
- Document identifier.
- Section and page information.
- Source metadata.

Vector similarity is useful for finding semantically related content, but it does not always retrieve exact technical terminology or specification identifiers.

This is why we will also use keyword search.

## 9. Hybrid Retrieval

The platform will combine semantic search with keyword-based retrieval.

### 9.1 Dense Retrieval

Dense retrieval uses embeddings to find passages with similar semantic meaning.

It is useful when a user asks a question using different wording from the original document.

### 9.2 Sparse Retrieval

BM25 will be used for keyword-based retrieval.

It is particularly useful for exact technical terms, acronyms, specification numbers and interface names.

For example, a search for a specific 3GPP clause or an interface identifier may benefit from keyword matching.

### 9.3 Combining Results

The two retrieval methods will produce separate candidate lists.

We will initially combine them using Reciprocal Rank Fusion (RRF).

\[
RRF(d)=\sum_{r \in R}\frac{1}{k+rank_r(d)}
\]

Where:

- \(d\) is a retrieved document chunk.
- \(R\) is the set of ranking lists.
- \(rank_r(d)\) is the rank of the chunk in a particular list.
- \(k\) is a smoothing constant.

This allows us to combine rankings without requiring the raw scores from different retrieval methods to be directly comparable.

## 10. Reranking

After hybrid retrieval, the system may contain several relevant candidates.

A reranker will evaluate the relationship between the query and each retrieved passage and produce a more precise ranking.

We will investigate a lightweight cross-encoder model from Sentence Transformers.

The initial retrieval workflow will be:

1. Retrieve candidates using dense search.
2. Retrieve candidates using BM25.
3. Combine rankings using RRF.
4. Remove duplicate chunks.
5. Rerank the candidate passages.
6. Select the most relevant context for generation.

Reranking introduces additional computation, so we will measure its effect on retrieval quality and latency.

If it does not provide enough improvement, we can keep it optional.

## 11. Query Processing

Questions about telecom documentation may contain abbreviations, technical terminology and references to specific procedures.

The system should support basic query processing.

Potential improvements include:

- Query normalisation.
- Acronym handling.
- Query rewriting.
- Breaking complex questions into smaller questions.
- Filtering by document source or version.

We will not automatically rewrite every query. Rewriting should be introduced when it improves retrieval performance.

For complex questions, the system may retrieve information from multiple documents and combine the evidence.

## 12. Answer Generation

The retrieved passages will be passed to a language model together with the user's question.

The generation prompt should instruct the model to:

- Answer using the supplied context.
- Avoid inventing technical requirements.
- Preserve important technical terminology.
- Distinguish facts from interpretation.
- State when the retrieved documents do not contain enough
